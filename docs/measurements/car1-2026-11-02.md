Car #1 (LAN 10.10.77.35) on a stand with its wheels in the air. Scripts are in `car/measure/` and run inside the
`MentorPi` container (`/home/ubuntu/shared` = host `~/docker/tmp`). Raw data is next to this file in `car1-2026-11-02/`.

Everything here is **measured on the car** unless it's marked *URDF* (Hiwonder's description file on the car: a
vendor source, not a measurement) or *code* (Hiwonder's code on the car).

## 3. Depth camera (HP60C, `ascamera`)

**Streams:** 640×480 RGB (`bgr8`) and 640×480 depth (`16UC1`). The depth image is **registered to the colour
image**: same intrinsics, frame `ascamera_color_0`.

**Intrinsics** (from `camera_info`):
- fx 594.9, fy 595.2, cx 343.4, cy 232.3; distortion all zero (plumb_bob)
- this gives an **FOV of 56.6° × 43.9°**
- **Conflict:** the product page says depth 73.8° × 58.8°, RGB 80.9° (research/03 §1.2), but the image the stack
  actually publishes is 56.6° wide. Check it with a tape measure: put an object at a known distance at the image
  edge.

**Mount:** `depth_cam` at x +0.064 m, 0.121 m above `base_footprint` (*URDF*).

**Frame rate.** Measured with `cam_rate.py` (10 s windows), then `measure_step.sh` after each change:

| Configuration | Camera publishes | Reader gets RGB / depth images | Worst gap |
|---|---|---|---|
| Stock (`fps: 15`, `color_pcl: True`, default Fast DDS) | 12.4 Hz | **4.8–5.8 / 5.8–6.1 Hz** | 0.97 s |
| + Fast DDS 8 MB shared-memory segment | 12.4 Hz | 12.4 / 12.4 Hz | 112 ms |
| + joystick busy-loop fix | 12.4 Hz | 12.4 / 12.4 Hz | 91 ms |
| + `color_pcl: False`, `fps: 30` | **24.8 Hz** | **24.8 / 24.8 Hz** | 55 ms |

**Findings:**
- The camera delivers about 0.82 × the configured fps.
- Stock Fast DDS uses a 512 KB shared-memory segment. A 0.9 MB frame doesn't fit, so it goes over fragmented UDP
  and gets dropped. `car/config/fastdds_shm.xml` fixes that.
- `joystick_control` ran at 100% of one core: `update_buttons` loops on `pg.event.get()` with no sleep. A 10 ms
  wait fixes it and brings it to about 6%.
- The point cloud `/depth0/points` still publishes, at 24.8 Hz.
- The web video server still works on port 8080.
- With all three changes: LiDAR, IMU and odometry rates are unchanged, and driving works.

**How the changes were applied, and how to revert:**
- Change → file in the container:
  - `export FASTRTPS_DEFAULT_PROFILES_FILE=…/fastdds_shm.xml` → `~/ros2_ws/.robotrc`
  - the busy-loop fix → `~/ros2_ws/src/peripherals/peripherals/joystick_control.py`
  - `color_pcl` and `fps` → `~/ros2_ws/src/peripherals/launch/include/ascamera.launch.py`
- Backups (with SHA256SUMS) are on the car at host `~/docker/tmp/camfps_backup/`.
- Revert with `bash ~/docker/tmp/camfps_backup/revert.sh`. A copy of the script is `car/config/camfps_revert.sh`.

## 4. Command latency (`step_test.py`, `analyse_step.py`)

**Method:** steering steps of ±30° straight to the servo, then drive steps of 0.2 and 0.4 m/s on
`/controller/cmd_vel`. The first IMU sample more than 6σ off baseline counts as the response. Run before and after
the camera changes (`step_test*_analysis.txt`).

| Path | Measured |
|---|---|
| `/controller/cmd_vel` → `/ros_robot_controller/set_motor` (ROS only) | 0.7–1.9 ms |
| Servo command → first IMU-visible steering motion | 36–73 ms (median about 52) |
| Drive command from rest → first IMU-visible motor motion | 51–71 ms |

**Reading these numbers:** the IMU samples every 20.6 ms, so the true start is up to about 21 ms earlier. That puts
command-to-motion at about 15–73 ms. The sim now uses `LATENCY_RANGE_S = (0.020, 0.070)` plus the 0–20 ms servo
dead time.

**Not measurable this way:**
- Servo travel time: the car keeps ringing on the stand for 0.24–0.9 s after each steering step, so it hides the
  end of the motion.

**No wheel feedback reaches ROS** (Hiwonder code on the car):
- The board protocol has no motor-feedback packet.
- `/odom_raw` (48 Hz) integrates the *commanded* speed in `odom_publisher_node.py`.
- `/odom` (30 Hz) is the EKF.
- Command mapping (*code* `ackermann.py`):
  - wheel Ø 0.067 m, wheelbase 0.145 m, track 0.133 m
  - steering clamped at ±40°, pulse = 1500 + 2000·deg/180
  - 0.2 m/s → 0.95 rps on motors 2 and 4, with motor 4 negated
